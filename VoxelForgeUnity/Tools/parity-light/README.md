# parity-light — сравнение воксельного освещения C# с JS-оригиналом исполнением

Проверяет, что `Assets/VoxelForge/Scripts/World/VF.Light.cs` и `World/VF.LightRules.cs` (а заодно начальный свет
генератора `Gen/GenWorker.cs` и `buildInitialPackedLightDense` из `World/VF.World.cs`) дают **ровно те же** массивы
света, что и оригинальный код `pretty.js`, на одних и тех же сценариях.

## Запуск

```sh
sh Tools/parity-light/run.sh <путь/к/pretty.js> [outDir] [--win=caves|ocean|pyramid] [--rounds=N]
```

* `outDir` по умолчанию — `$TMPDIR/vf-parity-light` (или `/tmp/vf-parity-light`).
* Без `--win` прогоняются все три окна (≈1 мин). `--rounds=N` меняет число раундов правок фазы B.
* Итог `light parity: OK` и код выхода 0 — паритет есть. При расхождении печатаются первые отличающиеся строки трассы,
  `FIRST_STEP=<n>`, затем оба драйвера автоматически перезапускаются с `--dump=<n>` и выводится повоксельная
  разница (координаты, id блока, sky/block-свет JS и C#).

Нужны `node` (22+), `mcs` и `mono`.

## Что делает

1. `jsenv-light.js` загружает `pretty.js` в node (данные `/*EXTRACTED ...*/` берутся из `Resources/VoxelForge`,
   браузерные API — инертная заглушка) и исполняет верхний уровень до таблиц блоков. Так в руках оказывается
   **настоящий** главный поток: хранилище чанков (`chunks`, `chunkFastGet`, секции), `getBlock`/`getBlockMeta` с
   картами меты и правок, весь движок света (`getPackedLightWorld` … `stitchChunkLight`, `processLightDirty`,
   `flushImmediatePlayerEditLighting`), а предикаты света (`lightStopsState`, `lightAttenuationState`, …,
   `isOpaque`, `axisLogIdSync`) дописываются дословно из конца файла. После загрузки песочница переводится в строгий
   режим: любое обращение к заглушке бросает исключение, т.е. JS-свет не может молча работать на заглушке.
2. `light-js.js` поднимает оригинальный gen-воркер (`GEN_WORKER_SOURCE`) в том же процессе и строит детерминированный
   сценарий для окна чанков (сиды и окна выбраны так, чтобы были пещеры, вода, лава, все виды листвы, лозы с ягодами,
   водоросли, пирамида с метаданными структуры):
   * **A** — загрузка чанков от центра (`integrateGenResult` + световая часть `createChunkFromData`: `stitchChunkLight`,
     постановка в очередь виртуальных источников из меты); у половины чанков «есть геометрия секций», чтобы
     `markLightDirtyChunks` шёл и по ветке `dirtySections`;
   * **B** — раунды правок у границ чанков и у края загруженной области: копание шахт (несколько правок в одном
     столбце → `skyDone`), крыши 3×3 (камень/стекло/листва/плиты/ступени), столбы воды и листвы, источники света
     (факел, лава, плачущий обсидиан, горящая печь, лишайник, магма, огонь, виртуальные GLOW и т.п.) и их удаление,
     удаление сгенерированных источников/воды/листвы/водорослей, виртуальные блоки (waterlogged-стекло, водные растения,
     смена меты на месте), лозы с ягодами + `repairLightAt`, края мира (y = 319/318/−63/−62, пустые секции),
     пара источников рядом (удаление более слабого), пакеты > 64 правок (уплотнение очереди), `processLightDirty`
     с бесконечным, прошедшим и далёким дедлайном, «игровые» правки через `flushImmediatePlayerEditLighting`
     (≤ 6 и > 6 правок), точечные запросы (`getPackedLightWorld`, `blockEmissionAt`, `lightStopsAt`, `lightCostAt`,
     `directSkyColumn`, в т.ч. вне мира и в незагруженном столбце);
   * **C** — догрузка последнего столбца чанков (стыковка с уже отредактированными соседями) и правки по новым границам;
   * **D** — выгрузка чанков с правками и повторная генерация с сохранённой дельтой.

   Правка повторяет всё, что в `setBlock()` относится к свету: карты меты, индекс правок, запись в секцию, сравнение
   `lightSignatureState` → `queueLightUpdate` + `notePlayerEditLight`. После каждой световой команды пишется снимок
   **всего** мира: FNV-хеши блоков и света каждой секции каждого чанка, `dirty/fullMeshDirty/meshRev/dirtySections`
   чанков, размеры очереди света; плюс строки генерации (свет воркера, `buildInitialPackedLightDense`, число
   sim/boundary-семян) и таблица предикатов для всех id × вариантов меты и всех виртуальных ключей.
3. `LightParity.cs` собирается `mcs` вместе со всеми скриптами проекта и копией `UnityStubs.cs`, где
   `Resources.Load<TextAsset>` читает файлы из `Resources/` (оригинальные заглушки не меняются). Он входит в
   `partial class VF`, вызывает настоящие `InitData` → `InitBlocks`, `GenWorker.Run`, `stitchChunkLight`,
   `processLightDirty`, `flushImmediatePlayerEditLighting`, `repairLightAt` и т.д., воспроизводит `scenario.txt`
   команда за командой и пишет `cs.txt` в том же формате. Печатает время, проведённое в коде света.
4. `compare.js` сравнивает трассы построчно, таблицы предикатов (как множества строк) и дампы (`--dump`).

## Покрытие JS-кода света

```sh
NODE_V8_COVERAGE=<outDir>/cov JSENV_DUMP=<outDir>/jsenv.json node Tools/parity-light/light-js.js <pretty.js> <outDir> caves
node Tools/parity-light/cover.js <pretty.js> <outDir>
```

Печатает строки 39 функций света, которые ни разу не выполнились. Остаются только недостижимые из игры
защитные ветки (`return` для y вне мира / незагруженного чанка внутри уже проверенных вызовов, секции без массива
света) и ветка «дедлайн истёк посреди пакета» в `processLightDirty` (зависит от времени).

## Мутационная проверка чувствительности

Если испортить в копии `VF.Light.cs` порог распространения (`nv > 1` → `nv > 2`), ослабление в столбце неба,
проход блочного света в `stitchChunkLight`, условие удаления неба, отметку `dirty` соседа по z или учёт
`waterlogged` в `VF.LightRules.cs` — сравнение падает (первое расхождение на шагах 2…1678).
